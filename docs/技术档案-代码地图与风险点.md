## 二、关键数据流

### 2.1 设备与密码存储

```
MainForm ──► DeviceStore ──► %APPDATA%\MyRemote\devices.json
     │
     └──────► CredentialVault ──► DPAPI ──► %APPDATA%\MyRemote\secrets.json
```

- 设备信息明文 JSON；密码单独加密。
- 首次保存用 `File.Move`，后续用 `File.Replace` + `.bak`。
- 凭据文件设置 Hidden + NTFS ACL（仅当前用户）。

### 2.2 RDP 会话

```
SessionForm ──► RdpHost(AxHost) ──► MsRdpClient9 ActiveX
                        │
                        ├── Server / UserName / Domain
                        ├── AdvancedSettings9.ClearTextPassword
                        ├── RedirectDrives / RedirectClipboard
                        └── DesktopWidth/Height / ColorDepth
```

- 使用 COM 后期绑定，Linux 交叉编译可行。
- 状态轮询 1 秒一次：`oc.Connected` 0/1/2/3。
- 首次连接 15 秒看门狗；断开可自动重连（最多 5 次，带 `_reconnectPending` 闸门）。

### 2.3 SMB 文件传输

```
FileManagerForm ──► NetworkShareHelper.AddCredential(CredWrite)
                        │
                        ▼
                UNC path \\host\share
                        │
                        ▼
                SmbTransferService.CopyFileAsync / CopyDirectoryAsync
                        │
                        └── .mrtmp → 校验大小 → File.Move 原子替换
```

### 2.4 一键修复 / 恢复

```
DiagnosticsForm ──► RepairService.RequestRepairAsync
                         │
                         ├── 已是管理员：直接 ExecuteRepair
                         └── 非管理员：runas 拉起自身 --repair（无界面子进程）
                                              │
                                              ├── CaptureSnapshot（注册表/服务/防火墙/网卡/自启）
                                              ├── FixItem（逐项）
                                              └── WriteResultFile
```

- 子进程通过 `--result <json>` 把结果写回主进程读取。
- 快照存在 `%APPDATA%\MyRemote\Rollback\snapshot_*.json`。

## 三、真机验证风险点逐项分析

### 1. UAC 提权链路

**源码位置：** `RepairService.cs` 的 `SpawnElevatedAsync`、`Program.cs` 的 `RunHeadlessRepair`

**流程：**
1. 主进程非管理员时，调用 `ProcessStartInfo` + `Verb = "runas"` 拉起自身。
2. 子进程参数 `--repair --items ... --result ...`。
3. 子进程 `Program.RunHeadlessRepair` 中 `_headless = true`，避免弹窗。
4. 子进程写结果文件，主进程读取。

**潜在风险：**
- `Application.ExecutablePath` 在单文件 publish 下是正确的 exe 路径；如果用户重命名 exe，自启和 runas 都会用这个路径，没问题。
- UAC 取消时：子进程 `ExitCode` 1223 或 `Win32Exception(1223)` 已处理。
- **风险点 A：部分系统上 UAC 弹窗后用户点了“是”，但子进程因为父进程工作目录或路径含空格解析失败。** 当前参数用双引号包裹了，较安全。
- **风险点 B：子进程执行时间超过 60 秒时，`RunCmd`/`RunPsFile` 会杀进程；但修复一般不会这么久。**
- **风险点 C：结果文件写入失败时主进程提示“未生成结果文件”。**

**建议补的日志：** 已在多处 `SystemLog.Info/Exception` 记录。如真机失败，看 `%APPDATA%\MyRemote\MyRemote.log`。

---

### 2. 网卡节能修复

**源码位置：** `DiagnosticsService.CheckNicPowerSaving`、`RepairService.FixItem(NicPower)` / `CaptureNicPower` / `RestoreNicPower`

**检测逻辑：** 读注册表 `SYSTEM\CurrentControlSet\Control\Class\{4d36e972-e325-11ce-bfc1-08002be10318}\xxxx\Device Parameters\PowerManagement\AllowComputerToTurnOffDevice`。

**修复逻辑：** `Get-NetAdapterPowerManagement | Set-NetAdapterPowerManagement -AllowComputerToTurnOffDevice $false`。

**潜在风险：**
- **风险点 A：注册表路径并非所有网卡驱动都写入。** 有些驱动（尤其 USB 网卡 / 虚拟机网卡）不在这里暴露电源管理项，检测会报“未读取到网卡电源设置”，但实际网卡可能有电源管理。这属于已知限制。
- **风险点 B：`Set-NetAdapterPowerManagement` 在部分网卡上不存在该参数，会报错。** 修复项会标记 failed。
- **风险点 C：某些网卡修改后需要重启才生效。** 这是硬件/驱动限制，程序无法绕开。
- **风险点 D：恢复时按适配器名还原；如果修改后适配器名变了（极少见），会失败。**

**建议：** 真机测试时若失败，需手动到设备管理器确认网卡电源管理标签是否存在。

### 3. SMB 免密

**源码位置：** `NetworkShareHelper.WriteCred`、`FileManagerForm.OnShown`

**逻辑：** 窗口打开时把 `host + user + password` 用 `CredWrite` 写入 `CRED_TYPE_DOMAIN_PASSWORD`，`Persist = ENTERPRISE`。

**潜在风险：**
- **风险点 A：凭据的 `TargetName` 是 host（即 `100.x.x.x` 或机器名）。** Windows 访问 `\\host\share` 时会按前缀匹配；如果用户用机器名连接但凭据 TargetName 是 IP，或反之，会不匹配。目前 TargetName 就是 device.Host，和 UNC 路径一致，应该 OK。
- **风险点 B：用户是微软账户（如 MicrosoftAccount\xxx@outlook.com）或域账号时，`UserName` 字段是否需要带前缀。** 当前代码把 `device.UserName` 原样写入。如果用户填的是 `xxx@outlook.com` 或 `DOMAIN\user`，会原样写入，通常 SMB 会正确识别。但如果用户只填了本地用户名，而目标机器是微软账户，会认证失败——这不是 bug，是配置问题。
- **风险点 C：旧版 cmdkey 存的凭据残留。** 编辑/删除设备时会 `CredDelete(host)`，但旧版 cmdkey 存的 TargetName 可能不同，需真机确认。
- **风险点 D：密码为空时跳过 CredWrite，文件管理会弹系统认证框。** 这是预期行为。

**建议：** 真机测试时，用 `cmdkey /list` 查看是否有重复/冲突的凭据。

### 4. 一键恢复

**源码位置：** `RepairService.ExecuteRestore`、`RestoreAll`

**逻辑：** 恢复快照中的：防火墙默认组启用状态、RDP 注册表、服务启动类型与运行状态、休眠、网卡节能、开机自启。

**潜在风险：**
- **风险点 A：防火墙默认组状态解析（`DefaultGroupEnabled`）依赖 netsh 输出中的“已启用 是/否”。** v1.6 已改为逐块解析，比较可靠。
- **风险点 B：`RestoreService` 用 `net start` / `net stop`。如果服务启动/停止失败（被依赖或依赖冲突），恢复项会失败但不会被提示。** 日志会记录。
- **风险点 C：网卡节能恢复依赖适配器名，如果修改后名变了会失败。**
- **风险点 D：恢复不会恢复被删除的自定义防火墙规则（只会删除 MyRemote-* 规则并恢复默认组）。** 这是设计如此。

**建议：** 修复前先记录当前状态，恢复后逐项比对。

### 5. RDP 实连

**源码位置：** `SessionForm.BeginConnect`、`RdpHost.cs`

**逻辑：** 设置 `Server`、`UserName`、`Domain`、`ClearTextPassword`、`RDPPort`、`RedirectDrives`、`RedirectClipboard`、`SmartSizing`、`AuthenticationLevel=2`、`EnableCredSspSupport=true`。

**潜在风险：**
- **风险点 A：中文用户名 / 微软账户 / 域账号。** `UserName` 支持 `DOMAIN\user` 拆分；微软账户通常写 `MicrosoftAccount\xxx@outlook.com` 或直接使用邮箱。如果用户只写本地账户名而目标要求邮箱，会失败。需要在 UI 或文档里明确提示。
- **风险点 B：`EnableCredSspSupport=true` + `AuthenticationLevel=2` 在某些 NLA 策略下可能要求证书或失败。** 这是企业环境常见坑。如果目标开了“仅允许运行使用网络级别身份验证的远程桌面的计算机连接”，当前设置应能过；但如果域策略强制 Kerberos 或证书，密码认证会失败。
- **风险点 C：RDP 连接时目标机器无密码或空密码。** Windows 默认禁止空密码远程登录，会失败。
- **风险点 D：目标机器是 Windows 家庭版。** 根本不能作为被控端，诊断里会标 Fail。
- **风险点 E：RDP 控件 `MsRdpClient9` 在旧版 Windows（如 Win10 1507）上可能不存在。** 但项目目标通常是 Win10/11，问题不大。

**建议：** 真机测试时，三种账号都测一次：本地账户、微软账户、域账户（如有）。

### 6. 全屏键盘

**源码位置：** `SessionForm.ToggleFullscreen`、`InitializeComponent` 的 KeyDown

**逻辑：** `KeyPreview = true`；F11 切换全屏；ESC 在全屏时退出全屏。全屏时保留工具栏可见，避免 RDP 抢键盘导致 F11 回不来。

**潜在风险：**
- **风险点 A：RDP 会话内嵌 ActiveX 捕获键盘焦点后，`SessionForm.KeyDown` 可能收不到 F11/ESC。** 这是 RDP ActiveX 的已知问题。当前方案是保留工具栏可见，用户可点按钮退出。
- **风险点 B：全屏时工具栏确实可见吗？** `ToggleFullscreen` 只改了 `FormBorderStyle` 和 `WindowState`，没有隐藏工具栏。所以工具栏应始终可见。
- **风险点 C：全屏后 `WindowState = Maximized` + `FormBorderStyle = None`，恢复时用 `_savedBounds`，多显示器环境下可能 bounds 已变。**

**建议：** 真机测试时，分别试键盘 F11/ESC 和工具栏按钮退出全屏。

### 7. 多机动态增减

**源码位置：** `MainForm.AddDevice`、`EditDevice`、`DeleteDevice`、`ImportFromTailscale`、`RefreshStatus`

**逻辑：**
- 设备存在 `devices.json`，动态增删改。
- 主界面每 30 秒对每个设备 TCP 探测 3389，更新状态列。
- 添加/导入后调用 `LoadDevices` 重建列表和 `_itemMap`。

**潜在风险：**
- **风险点 A：并发刷新。** 每次 `RefreshStatus` 对每个设备启动一个 `Task.Run`；30 秒一轮。如果设备多或网络慢，可能累积大量任务。当前无取消机制，但 `IsPortOpenAsync` 有 2 秒超时，任务量可控。
- **风险点 B：`_itemMap` 在 `LoadDevices` 时重建，但正在进行的 `RefreshStatus` Task 可能引用旧的 item。** 代码里 `Invoke` 前检查 `_list == null || _list.IsDisposed || !_list.IsHandleCreated`，但 `_itemMap.TryGetValue` 可能拿到旧 item（虽然 Id 一样，引用不同）。这里潜在有轻微不一致，但通常不会崩。
- **风险点 C：导入 Tailscale 设备时只按 IP 去重，如果同一机器有多个 IP（IPv4/IPv6）会导入两次？** 代码 `devices.Any(d => d.Host.Equals(peer.Ip, ...))` 只按导入的 IPv4 去重，如果已有设备用机器名、新导入用 IP，会重复。

**建议：** 真机测试时，添加、编辑、删除、导入都操作一遍，看状态刷新是否正常。

## 四、其他潜在代码债

1. **日志路径硬编码：** `AppPaths.AppDir` 用 `%APPDATA%\MyRemote` 或便携模式 exe 同目录。无问题。
2. **单文件 publish 不支持 trim：** `<PublishTrimmed>false</PublishTrimmed>`，产物大但稳。
3. **`CredentialVault` 异常静默吞掉：** `LoadMap` 和 `SaveMap` 有 try/catch，失败只记日志。如果 DPAPI 失败，用户会表现为密码每次都要重新输入。
4. **`NetworkShareHelper.AddCredential` 失败不弹窗：** 仅记日志，文件管理首次访问会弹系统认证框。这是安全设计。
5. **`MainForm.RefreshStatus` 不等待完成：** 30 秒触发一轮，旧任务可能还在跑。如果设备很多，建议加 `CancellationToken` 或限制并发。
6. **`DiagnosticsService.RunAll` 使用 `[ThreadStatic]` 缓存防火墙转储：** 如果在多线程调用会每个线程各转储一次；当前只在诊断窗体单线程调用，OK。
7. **异常处理偏宽容：** 很多地方 catch 后静默忽略，优点是程序不易崩，缺点是问题不易暴露。真机验证阶段建议适当加日志。

## 五、下一步建议

按优先级排序：

1. **先跑环境诊断 + 一键修复**，确认 UAC 链路、服务、防火墙、RDP 注册表都 OK。
2. **在两台机器上互连 RDP**，优先用本地账户，再试微软账户/域账户。
3. **测试文件管理免密**，看首次访问是否弹系统认证框。
4. **测试一键恢复**，修复后再恢复，对比 netsh 规则变化。
5. **测试网卡节能**，这是最容易因硬件差异失败的项。
6. **全屏键盘和多机增减** 放在最后，属于 UI 体验项。

遇到任何异常，先看 `%APPDATA%\MyRemote\MyRemote.log`。
