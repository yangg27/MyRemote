## 二、已知缺陷与技术债

### 2.1 已知缺陷（按影响排序）

| # | 缺陷 | 影响 | 严重度 | 是否可解 |
|---|---|---|---|---|
| 1 | **网卡节能诊断在部分硬件上失效** | 某些驱动（USB 网卡/虚拟机网卡）不在注册表暴露该键，检测报"未知" | 中 | ⚠️ 部分（驱动相关，无法完全覆盖） |
| 2 | **企业网严格限 UDP 时走 DERP 中继** | 速度退化到"类商业远控"体验（但仍是端到端加密） | 中 | ⚠️ 换公司 VPN / ZeroTier |
| 3 | **诊断 15 项中有 3 项依赖网络实时状态** | 离线/网络抖动时结果不稳定 | 低 | ✅ 设计如此（可加"稳定化"逻辑） |
| 4 | **无 ARM64 交付包** | ARM 设备需用 x64 版（走模拟层，性能有损） | 低 | ✅ 完全可解（见路线图 #2） |
| 5 | **产物体积 161 MB** | 分发体积大（zip 后 63 MB） | 低 | ⚠️ 裁剪风险高，暂不改 |
| 6 | **单文件 exe 首次启动稍慢** | 需解压到临时目录（约 1–3 秒） | 低 | ⚠️ 单文件机制固有 |
| 7 | **RDP 会话窗口内 F11/ESC 可能被远端捕获** | 已知 ActiveX 问题（已用"工具栏保持可见"缓解） | 低 | ⚠️ 缓解已足够 |
| 8 | 微软账户 / 域账户需用户自行填对格式 | 配置问题非缺陷，但易用性欠佳 | 低 | ✅ 可加输入提示 |

### 2.2 技术债清单

| # | 技术债 | 位置 | 建议 |
|---|---|---|---|
| 1 | **异常处理偏宽容** | 多处 `catch { }` 静默忽略 | 优点是不易崩，缺点是问题不易暴露。建议在**关键路径**补日志（当前已在主要路径补齐，长尾仍需梳理） |
| 2 | `RefreshStatus` 无取消机制 | `MainForm` | 每 30 秒对每设备起 `Task.Run`，无 `CancellationToken`。设备多时任务可能堆积（当前每任务 2 秒超时，风险可控） |
| 3 | `_itemMap` 潜在引用不一致 | `MainForm.LoadDevices` | 重建 map 时正在跑的刷新任务可能引用旧 item（Id 一致，通常不崩）。建议改为按 Id 查找 |
| 4 | Tailscale 导入去重只按 IP | `MainForm.ImportFromTailscale` | 若已有设备用机器名、新导入用 IP，会重复。建议按 IP+机器名双键去重 |
| 5 | `DiagnosticsService` 单文件 915 行 | — | 建议按检测分组拆成 partial 类（可读性） |
| 6 | `RepairService` 单文件 1000 行 | — | 同上。或抽出快照/修复/恢复三个 partial |
| 7 | 无 CI/CD | 仓库 | 建议加 GitHub Actions 做 `dotnet build` + 探针 `--func` 冒烟（Windows runner） |
| 8 | 无自动化单元测试框架 | 仓库 | 探针已覆盖大量场景，可考虑将断言迁移到 xUnit（非必需） |
| 9 | `一键部署.ps1` 已是历史遗物 | `src/` | 功能已被内置"一键修复"取代，保留仅为兼容老流程。建议在 v2.0 移除 |

## 三、后续优化方向（按优先级）

### 🔴 P0 —— 建议优先做（低成本高收益）

#### 1. 补 ARM64 交付包

**为什么**：老版本（v1.4/v1.5）曾提供 `MyRemote-arm64.exe`，当前 v1.7 只有 x64。ARM 设备（骁龙本、Surface Pro X）在跑模拟层，RDP 会话流畅度会受影响。

**怎么做**：

```bash
dotnet publish MyRemote/MyRemote.csproj -c Release -r win-arm64 -o <输出目录> \
  -p:IncludeNativeLibrariesForSelfExtract=true
```

交付包内同时放两个 exe，`使用说明` 里说明如何选择。

**成本**：约 20 分钟（编译 + 验证 + 改说明）。

#### 2. CI 自动化（GitHub Actions）

**为什么**：目前验证全靠人工跑。接手者改动后可能忘记跑自检。

**怎么做**：`.github/workflows/build.yml`

```yaml
runs-on: windows-latest
steps:
  - dotnet build MyRemote/MyRemote.csproj -c Release
  - dotnet build MyRemote.Probe/MyRemote.Probe.csproj -c Release
  - ./MyRemote.Probe/bin/Release/net8.0-windows/win-x64/MyRemote.Probe.exe --func
    # 断言 0 失败则通过
```

**成本**：约 1 小时。**收益**：防回归。

#### 3. 诊断项扩展到 20+ 项

**可加的高价值项**：

| 候选诊断项 | 检查方式 | 价值 |
|---|---|---|
| 系统时间是否准确 | `w32tm /query /status` | RDP/Kerberos 认证失败的常见原因 |
| 磁盘空间是否充足 | 系统盘剩余空间 | 快照/日志写不进去会静默失败 |
| 网络类型（公用/专用） | 注册表 | "公用网络"会影响 SMB 与发现 |
| RDP 监听端口是否真在监听 | `netstat -an \| findstr 3389` | 比注册表更直接的证据 |
| Tailscale 版本是否过旧 | `tailscale version` | 老版本有已知 bug |
| Windows 更新状态 | — | 老系统 RDP 有已知漏洞 |
| 是否有第三方远控软件冲突 | 进程扫描 | 向日葵/ToDesk 可能占用端口 |

**成本**：每项约 30 分钟。

## 四、架构演进建议（长期）

### 4.1 如果要支持更多协议

当前架构对 RDP 是"专用"的（`SessionForm` 直接嵌入 RDP ActiveX）。
若要支持 VNC / AnyDesk 等，建议抽象出接口：

```csharp
interface IRemoteSessionHost
{
    void Connect(Device device, Credentials cred);
    event EventHandler<SessionState> StateChanged;
    Control GetView();      // 返回可嵌入的 UI 控件
}
```

然后 `RdpSessionHost` / `VncSessionHost` 各自实现。**当前不需要做**（YAGNI），但新增协议时值得先做这层抽象。

### 4.2 如果要拆分成"服务端 + 客户端"

当前是**每台机器跑同一个 exe，角色完全对等**，这是最简设计（也是需求决定的：单人使用、设备对等）。

若未来要支持"一台中心控多台"（类似团队运维面板），需要：
- 被控端常驻服务（Windows Service）
- 控制端只装 UI
- 引入设备发现/注册机制

**这是架构级变更，不建议在当前规模下做。**

### 4.3 如果要支持非 Windows 被控端

RDP 是 Windows 专有。若要对 Linux/macOS：
- 被控端用 xrdp（Linux）/ 系统自带屏幕共享（macOS）
- 客户端仍可用 RDP 控件（xrdp 兼容 RDP 协议）
- 文件传输改用 SFTP（Linux）/ AFP（macOS）

**工作量中等**，主要成本在跨平台测试。

## 六、当前版本的"不要动"清单

这些地方看起来可以简化，但实际上**有历史原因，别轻易改**：

| 代码 | 别动的原因 |
|---|---|
| `UiScale` 显式换算 + `AutoScaleMode.None` | 换成自动缩放会破坏已验证的布局矩阵 |
| 数据类必须是属性不能是字段 | P0 序列化缺陷的修复，改回字段等于恢复那个 bug |
| `ExplainInvalidSnapshot()` 校验 | 安全防线，删了可能让空快照重写系统 |
| `netsh` 而非 PowerShell cmdlet | cmdlet 在目标机实测不可用 |
| `GetACP()`/`GetOEMCP()` 而非 `CultureInfo` | `InvariantGlobalization=true` 下代码页错误 |
| 三层 Tailscale 读取 fallback | 不同版本/权限下行为不同 |
| `RdpClientDetector` 动态探测 | 硬编码 CLSID 在部分系统未注册 |
| `--result` JSON 文件 IPC | 子进程是独立进程，需要结构化回传 |
| 探针工程 | 质量的唯一保障，别删 |
| `File.Move` 首次保存分支 | `File.Replace` 要求目标存在 |
